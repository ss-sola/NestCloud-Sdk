# 写请求幂等

## 接入条件

启用 TypeORM 的服务可注入 `DatabaseIdempotencyService`。鉴权和 DTO 校验沿用原接口，在控制器已经得到有效入参后，将稳定的服务及操作名、影响本次写入的字段和业务回调交给 `executeHttp`。首批 `PUT /file/description` 使用固定的成功 HTTP 状态和 JSON 业务响应。下载流、Cookie、动态状态码及事务外副作用需要独立处理。

受保护写入必须全部使用接收服务同一个 PostgreSQL 数据库和事务。基类 CRUD 自动使用当前事务管理器。自定义查询应使用 `BaseService.entityRepository`，已有代码持有的常规 Repository 和自行开启的事务需要在启用重试前审核。网络调用、投递消息、写文件和调用模型无法随 PostgreSQL 回滚，首批只保护文件描述的数据库更新。后续异步写应使用事务内的持久任务及支持去重的消费者。

## 数据与故障语义

`rpc_idempotency_record` 以“操作名、调用主体、Idempotency-Key”的摘要作为主键。请求指纹按业务字段生成，忽略对象属性顺序并保留数组顺序。受限接口从服务器已验证的会话取账号。文件描述原本允许公开调用，其键空间固定，并将首次调用身份计入指纹。会话在两次尝试之间改变会返回冲突。

首次请求在同一事务中占键、修改业务数据、保存 JSON 结果再提交。并发实例等待同一唯一键。若首次已提交，后续相同请求直接回放；若首次事务回滚，等待者可以接管。超过 3 秒仍等待占键时返回 503；同键异参返回 409；无效键返回 400。存储不可用时有键请求在执行业务前失败，已开启的事务随故障回滚。无键调用沿用原接口的单次执行语义。

记录长期保存以覆盖延迟重投，不设置 TTL。清理记录会让迟到的旧键能够重新占用。数据库备份和恢复必须覆盖业务数据及幂等表，并保持在同一恢复点。

## 发布与回退

1. 在接收幂等写入的业务服务所在 PostgreSQL 数据库执行 NestCloud 仓库的 `sql/sdk/add-rpc-idempotency-record.sql`。例如，SolaCloud 的 middleware-service 需要在保存文件描述的业务库执行该脚本，新库在业务表初始化后执行。
2. 升级全部提供文件描述更新的 middleware-service 实例，包括固定地址和网关后端。随后升级调用方。新客户端即使关闭重试也会在首发带键，因此新接收实例要先准备好表。
3. 在调用方 rag-service 设置公共配置 `RemoteWriteRetryEnabled=true`。默认值为 `false`。开关只影响已声明幂等写的命名服务调用。
4. 回退时先在所有调用方关闭写重试并等待在途调用结束，再回退接收实例。保留幂等记录供后续使用。

## 复验跨实例写入

为专项测试提供可创建 schema 的独立 PostgreSQL 数据库，通过 `NEST_CLOUD_TEST_POSTGRES_URL` 指定连接串。SDK 默认读取同级仓库中的 `../NestCloud/sql/sdk/add-rpc-idempotency-record.sql`。单独检出 SDK 时，可通过 `NEST_CLOUD_TEST_RPC_SCHEMA_FILE` 指定从 NestCloud 取得的同一文件；相对路径以测试命令的工作目录为准。测试在随机 schema 中执行该脚本并创建业务表，结束后清理。

在 SDK 根目录执行以下命令。第二个命令使用同级目录的 SolaCloud 工作区，该工作区须先安装当前 SDK 的构建产物。

```sh
pnpm exec vitest run src/__tests__/database/database-idempotency.postgres.spec.ts
pnpm --dir ../SolaCloud/apps/middleware-service exec vitest run --config ../../scripts/vitest.backend.e2e.config.ts src/__tests__/file-retry.e2e-spec.ts
```

第一个用例组使用两个独立连接池，验证并发占键、等待超时及回滚后的接管。第二个用例组启动两个 Nest HTTP 实例，让第一个实例在事务提交后断开响应连接；用触发器统计实际 UPDATE 次数，并核对两个实例收到的操作键、链路 ID 和 span。
