# 链路传递与重试

## 如何追踪一次调用

公共 HTTP 入口接续 W3C `traceparent` 和 `tracestate`。缺少有效父上下文时生成新链路。响应头 `x-trace-id` 可用于检索服务日志。每次 HTTP 请求、Worker 消费和客户端发送尝试都有自己的 span，同一次调用的所有尝试共享 trace ID。业务进程注册了 OpenTelemetry tracer 时可以使用已有采集配置，默认通过日志查看链路。

入队时保存当前 span 的传播头。Worker 在恢复后的上下文中等待处理结果，异常交给 BullMQ。链路 ID 只关联日志，同一个链路中的多个写入各自使用独立的操作键。

## 客户端重试策略

| 方法选项                    | 自动重试条件                                                                                             |
| --------------------------- | -------------------------------------------------------------------------------------------------------- |
| 省略 `retry`                | 单次发送，沿用原有超时                                                                                   |
| `retry: 'read'`             | 调用方已确认该命名服务的接口只读。首批为 `POST /file/batch-detail`                                       |
| `retry: 'idempotent-write'` | 每次逻辑调用生成或领取同一个操作键。接收端升级并在调用服务配置 `RemoteWriteRetryEnabled=true` 后允许重发 |

最多 3 次（含首次），全部请求与退避共用 20 秒预算。单次默认 10 秒，方法级 `timeout` 单位为秒。对已开启重试的操作，`timeout: 0` 仍受总预算约束。重试优先选尚未尝试的实例地址；使用固定地址时重试该地址。

连接重置、连接拒绝、临时 DNS 故障、请求超时以及 HTTP 502、503、504 可触发重试。429 需要有效的 `Retry-After`。延迟取指数随机退避与服务端要求等待时间的较大值，超过剩余预算直接结束。一般业务错误、401、403、409 和 500 均直接返回给调用方。任意绝对 URL 按单次调用处理。重试次数、预算、错误名单和退避起点集中在 `src/constants/remote-retry.constants.ts`。

## 子操作

HTTP 重试由客户端在一个逻辑调用内固定 `Idempotency-Key`。跨任务重投时，应从稳定的任务身份和业务步骤生成键，在单个出站调用上使用 `ContextService.withOperationKey`。对于单发的上游编排调用，显式指定的身份通过 `x-operation-id` 送达。下游按具体写入步骤调用 `deriveOperationKey`，从而区分同一任务内的独立写入。两个头均不提供身份验证。
